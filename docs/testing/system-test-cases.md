# EventHub system test cases (Part 5)

**CEN 4020 AI Project, Part 5, Deliverable 4 · Team: Ian Koratsky, Minh Tam Nguyen**

The system tests drive the real application in a real browser (Selenium WebDriver + Chrome) against a real PostgreSQL. They run with one command, on every code change in GitHub Actions, and from a Run workflow button. Each run writes a pass/fail report.

- **Full list of every case** (ID, expected result, black/white-box, requirements): [system-test-catalogue.md](system-test-catalogue.md), generated from the test code.
- **Code:** [`tests/system/`](../../tests/system/)
- **Latest report:** `reports/system-tests.html` after a run. A copy of the final Part 5 run is in [`docs/evidence/system-tests/`](../evidence/system-tests/).

## Run them

| How | Command |
|---|---|
| Windows: double-click | `run-system-tests.cmd` in the project folder (opens the report when done) |
| Any OS, one command | `python scripts/run_system_tests.py` |
| Watch the browser | `python scripts/run_system_tests.py --headed` |
| Another browser | `python scripts/run_system_tests.py --browser edge` (or `firefox`) |
| One test | `python scripts/run_system_tests.py -k st30` |
| GitHub | Actions → System tests → Run workflow. It also runs on every push and pull request. |

The runner starts the throwaway PostgreSQL from `docker-compose.test.yml` if `EVENTHUB_TEST_DATABASE_URL` is not set, resets it, starts EventHub on a free local port, and runs the tests. It writes:
- `reports/system-tests.html`: one row per test, with its requirements, kind and result, plus a browser screenshot for every failure;
- `reports/system-tests.xml`: JUnit, for CI;
- `reports/screenshots/`: a PNG of each failing browser.

## How the suite is built

| Piece | What it does |
|---|---|
| `tests/system/conftest.py` | Resets and seeds the database and creates an admin. Serves `create_app()` on a free port, or uses `EVENTHUB_BASE_URL` for an already-running server. Keeps a pool of browsers, takes failure screenshots, adds the report columns. Refuses to run a test that does not name a real requirement (system-015). |
| `tests/system/support.py` | `EventHub`: a page object that does only what a person can do (open, type, click, read). `Database`: arranges test data (an event with one ticket, an event that started yesterday) and fast-forwards time for white-box cases. |
| `@pytest.mark.requirement(...)` | Every test names the requirement ids it proves (Thuy: "every test carries a requirement reference"). |
| `@pytest.mark.whitebox` | Marks cases designed from knowing the code. Everything else is black-box: designed from `features/*/requirements.md` and the Call 5 transcript only. |
| `scripts/check_requirement_coverage.py` | Lists requirements that no test names. CI fails if a testable one appears. |

## White-box edge cases (from knowing the code)

| Edge case | The code fact behind it | Test |
|---|---|---|
| Quantity "²", "①", "٣" | Quantities and URL ids were checked with `str.isdigit()`, which is True for these characters, but `int("²")` raises `ValueError`. Result: HTTP 500, and "٣" was quietly bought as 3 tickets. | ST-20 |
| `/events/²`, `/orders/①`, `/checkout/²` | `db_id()` and the catalog/orders services used the same `isdigit()` check: 500 on a GET | ST-21 |
| A 5,000-digit quantity | Python refuses `int()` on strings over 4,300 digits, so the length must be checked first | ST-23 |
| Pay after the 10-minute hold ran out | Expiry is checked at payment time in the database clock; fast-forwarded with SQL | ST-60 |
| Admin changes a rate while a buyer is at checkout | The quote is frozen on the hold (purchase-013) | ST-61 |
| Idle for 31 minutes | Server-side session idle timeout; fast-forwarded with SQL | ST-62 |
| 45.00 USD -10% × 0.79 = 31.995 | Discount → convert → round half-up once (ADR-005) | ST-63 |
| `NAME@USF.EDU`, `name+party@`, `mail.usf.edu`, `usf.edu.evil.com`, `notusf.edu` | `evaluate_student_eligibility()` compares the exact domain after case-folding | ST-64 |
| Two browsers press Continue for the last ticket at once | The event row is locked (`SELECT ... FOR UPDATE`) before the hold | ST-65 |
| Search for `%`, `_`, `\`, `' OR 1=1 --` | Search uses SQL `ILIKE` with escaping | ST-66 |
| Every outcome in the audit log, with every field | The audit write is inside the purchase transaction | ST-67 |
| Admin rate 0, -1, "abc" | Rate validation in `AdminService` | ST-68 |
| Event starting in 5 minutes | Boundary of the new sales-closed rule | ST-69 |
| Passwords in the database | PBKDF2 hashes only | ST-56 |

## Performance (system-013)

ST-70 signs up 20 buyers, then all 20 buy 3 tickets each at the same time (120 timed purchase requests: checkout start and payment). It passes if 95% finish within 1 second and none fails with a server error. The target is `[TEMPORARY_MVP_DEFAULT]` until Marcus supplies the sentence. It can be changed with `EVENTHUB_PERF_P95_SECONDS`, and the buyers and purchases with `EVENTHUB_PERF_BUYERS` / `EVENTHUB_PERF_PURCHASES`.

Measured on the development laptop (Windows 11, Werkzeug threaded server, PostgreSQL 16 in Docker), three runs: median 0.19–0.20 s, p95 0.29–0.36 s, max 0.40–0.46 s ([log](../evidence/system-tests/performance-st70.log)).
